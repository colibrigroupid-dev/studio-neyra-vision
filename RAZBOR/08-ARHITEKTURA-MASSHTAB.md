# Архитектура платформы целиком: от прототипа до 10 000 человек

Установка Александра 13.10.2026 01:43: видеть проект целиком, продумать на будущее, масштабирование 100 → 1 000 → 10 000 человек (команды и одиночные пользователи), экосистема и код такие, чтобы подключались команды программистов и писали отдельные блоки.

Этот документ — карта всей системы. Правило для всех, кто пишет код: **новый код кладётся в блок с границей (контракт API, свои данные, свои тесты), а не «куда удобно»**.

## 1. Экосистема одной картиной

```
 ┌──────────────── Витрина studio.neyra.vision (статика) ────────────────┐
 │ главная RU/KZ · страницы проектов по коду (сборка из ДРК) · документация│
 └───────────────────────────────┬─────────────────────────────────────────┘
                                 │
 ┌─────────── Кабинет и окно проекта (веб-приложение, модули) ───────────┐

 │ Раскадровка · Кадры · Непрерывность · Звук · Монтаж · План и смета ·    │
 │ Карта производства · ДРК и выгрузка · Журнал                            │
 └───────────────────────────────┬─────────────────────────────────────────┘
                                 │  HTTPS, JSON, один контракт (OpenAPI)
 ┌──────────────────────── Ядро (API) ────────────────────────────────────┐
 │ Студии и пользователи · Проекты и участники · Сущности кино ·           │
 │ Версии · Клетки карты и апрувы · Журнал происхождения (append-only) ·   │
 │ Файлы (ссылки на хранилище) · Задания генерации (очередь) · Биллинг     │

                                        │
 ┌──────────────── Воркеры генерации (отдельные процессы/машины) ─────────┐
```

Принцип: **ядро не знает про модели и интерфейсы**, оно знает про сущности кино и права. Генераторы и интерфейсы подключаются снаружи через контракты.

## 2. Модель данных (ядро) — то, что не меняется при росте

| Сущность | Ключевые поля | Зачем |
|---|---|---|
| **Студия** (tenant) | id, название, план/кредиты, настройки, ключи провайдеров (зашифрованы) | изоляция данных и счёт: всё принадлежит студии; одиночный пользователь = студия из одного человека |
| **Пользователь** | id, анкета (§4б), способы входа (e-mail, Telegram), студии и роли в них | один человек — много студий и проектов |
| **Проект** | id, студия, slug, название RU/KK, тип, статус, стиль мира, коды доступа, настройки | единица работы |
| **Участник** | пользователь × проект × роль × разделы × ответственности | права и ответственность |
| **Сцена** | проект, номер, слаглайн, текст, порядок, акт | из разбивки |
| **Герой / Локация / Объект мира** | проект (или студия — библиотека), паспорт, замок (текст + референсы), статус, версии | аватары и места |
| **Кадр** | сцена, номер, спецификация (крупность, движение, объектив, длительность), варианты, выбранный, статус, замечания | единица производства |
| **Файл** | id, владелец-сущность, хранилище-ключ, тип, размер, хэш, **происхождение** (инструмент, модель, промпт, параметры, цена, кто, когда) | всё, что сгенерировано или загружено |
| **Версия** | сущность, номер, автор, дата, снимок, метка | история без перезаписи |
| **Клетка карты** | объект × этап, исполнитель, утверждающий, статус, срок | карта производства |
| **Апрув** | объект, версия, кто, когда, вердикт, комментарий (append-only) | ответственность |
| **Событие журнала** | студия, проект, кто, что, объект, когда, хэш (append-only) | ДРК, лента, аудит |
| **Задание генерации** | тип, вход, параметры, статус, воркер, стоимость, результат → Файл | очередь и биллинг |
| **Права** | сущность доступа (студия, проект, раздел, объект), субъект (пользователь, роль, ключ, ссылка-код), действие (читать, писать, утверждать) | единая проверка на сервере |

Идентификаторы — глобальные (ULID), чтобы данные переезжали между серверами без перенумерации. Все записи несут `studio_id` — изоляция арендаторов проверяется в одном месте.

## 3. Блоки (модули) и их границы — так подключаются команды программистов

Каждый блок = папка `blocks/<imya>/` со своим `README.md` (что делает, контракт, кто владелец), `api/` (маршруты и схемы), `tests/`, `ui/` (если есть экран). Блок обращается к другим блокам **только через их API или события**, не через чужие таблицы.

| Блок | Отвечает | Контракт наружу | Текущее состояние |
|---|---|---|---|
| `core-auth` | студии, пользователи, вход (e-mail, Telegram), сессии, права | `/api/me`, `/api/auth/*`, проверка прав | ключи ролей в прототипе (№15), кабинет №36, вход №20/№37 |
| `core-projects` | проекты, участники, настройки, коды страниц | `/api/projects*` | есть (№15, №35) |
| `scenariy` | драфты, версии, Fountain/FDX, ассистент NEYRA | `/script`, `/versions`, события «версия принята» | редактор `scenariy/` (№03), сервер есть |
| `razbivka` | сцены, герои, локации из текста | `POST /breakdown` → сущности | `tools/razbivka.py` (№18) → перенести в блок |
| `geroi-i-lokacii` | паспорта, замки, библиотека студии, листы | `/heroes`, `/locations`, `/library` | формат карточек (№19) |
| `raskadrovka` | шот-листы, карандаш, контактные листы, аниматик | `/shots`, задания генерации | №24 |
| `kadry` | карточка кадра, варианты, статусы, чистовик, видео | `/shots/<id>/variants` | формат есть (№06), UI в окне |
| `neprerivnost` | сверка кадров с замками | события «кадр принят» → замечания | №22 |
| `zvuk`, `montazh` | звук, монтаж, мастер | задания, файлы | навыки Киностанции → блоки позже |
| `karta` | клетки, апрувы, зависимости, лента | `/map`, `/cells`, `/approvals`, `/activity` | есть (№31), экран №32 |
| `drk` | происхождение, права, экспорт ZIP/манифест/паспорт, чек-лист «готов к продаже» | `/export`, `/provenance` | №27–28 |

| `vitrina` | статика сайта, страницы проектов, сборщик | `tools/build-project.py` → читает ДРК через API | есть (папка) → перевести на API |

Правило границ: блок может читать чужие сущности через API ядра, писать — только свои. Любой новый генератор — только через `generatory` и только с происхождением. Любой новый экран — только через опубликованный контракт.

## 4. Контракты и события

- **OpenAPI** — один файл `contracts/openapi.yaml`, источник правды для фронта, CLI, ботов и агентов; из него — типы и тесты контрактов. Сейчас `server/API.md` — описание словами; перевести в OpenAPI (№39).
- **События** (шина): `project.created`, `script.version.saved`, `script.version.approved`, `hero.locked`, `shot.variant.created`, `shot.approved`, `shot.returned`, `cell.status.changed`, `file.created`, `job.finished`, `member.added`. Подписчики: карта, непрерывность, уведомления, ДРК, биллинг. Каждое событие — запись журнала.
- **Задания генерации**: `{type, input, params, requested_by, project, budget_limit}` → очередь → воркер → `{file, provenance, cost}`. Повтор идемпотентен (ключ задания), оплата списывается при успехе, отказ бесплатен (урок Neyra Play).
- **Права** проверяются ядром на каждом запросе по таблице прав; UI их не изобретает.

## 5. Как это масштабируется

| Уровень | Люди | Что стоит | Что меняется в коде |
|---|---|---|---|
| **Сейчас (прототип)** | 1 студия, 5–10 человек | один сервер Python (stdlib), JSON-файлы, статика на GitHub Pages, генерация на Mac | ничего — но блоки уже разделены по папкам и контрактам |
| **100** | 5–10 студий | один сервер в Казахстане (Docker): API + Postgres + S3-совместимое хранилище (MinIO) + Redis-очередь + 1 GPU-воркер; HTTPS; бэкапы | JSON-файлы → Postgres (схема §2), файлы → S3, задания → очередь; код блоков не меняется, меняется слой хранения |
| **1 000** | 50–100 студий | API в 2–3 копиях за балансировщиком, отдельный сервер БД, отдельные воркеры по типу заданий (карандаш/картинка/видео), CDN для витрины и медиа, мониторинг и логи | блоки выделяются в отдельные процессы по мере нагрузки (генераторы — первыми); события по шине |
| **10 000** | сотни студий, одиночки | мультирегион (Казахстан + ещё один), шардирование по студиям, очереди с приоритетами, тарифы и биллинг, SLA, аудит безопасности, самообслуживание регистрации | те же контракты; появляются команды по блокам, релизы по блокам, флаги функций |

Что закладываем уже сейчас, чтобы переход не ломал: `studio_id` везде; ULID; append-only журнал; файлы по ссылкам, а не в БД; задания через очередь даже если воркер один; права через ядро; контракт API версионируется (`/api/v1`).

## 6. Технологии (решение по умолчанию, менять можно по блоку)

- **Ядро:** Python 3.12, FastAPI, Postgres, SQLAlchemy/Alembic (миграции), Redis (очередь, сессии), S3-совместимое хранилище. Прототип на stdlib переезжает блоками, тесты остаются.
- **Интерфейсы:** статика без сборщика остаётся для витрины; окно проекта — модульный JS по блокам (ES-модули, один дизайн-токен-файл, компоненты карточек/карты), при росте команды — переход на сборку (Vite) без смены контрактов.
- **Воркеры:** Python, Docker, GPU по требованию; каждый генератор — отдельный образ с одним интерфейсом.
- **Инфраструктура:** Docker Compose на один сервер → Kubernetes/Nomad при 1 000; резервные копии ежедневно; секреты в хранилище секретов, не в репо.
- **Качество:** тесты контрактов на каждый блок, проверка партнёром (Claude/Codex) по `PROVERKA.md`, CI на каждый push, релиз блоками с номером выката.

## 7. Как подключается команда программистов

1. Читает `AGENTS.md`, этот документ и `contracts/openapi.yaml`.
2. Берёт блок с доски; у блока один владелец-команда и один проверяющий.
3. Пишет в `blocks/<imya>/` по контракту; чужие таблицы и файлы не трогает; новые события — в список §4.
4. Сдаёт с тестами и записью в журнал; принимает партнёр-проверяющий; выкат — отдельный номер.
5. Интерфейс блока — по дизайн-токенам и правилам веб-мастера (простота для киношников, казахский, 375 px).

Переезд в эту структуру — не разом, а блоками, когда блок получает второго разработчика (№40).

## 9. Риски и что с ними
- **Зависимость от закрытых моделей** (Nano Banana, Seedance, Neyra) — адаптеры и происхождение: модель меняется, фильм остаётся.
- **Казахстан и трафик** — хранилище и воркеры в КЗ, CDN для витрины.
- **Права на контент** — ДРК и цепочка прав с первого дня (§6 в `RAZBOR/06`).
- **Две системы правды (папка и сервер)** — папка для Александра, сервер для команды, синхронизация с ревизиями (№29); при росте источник правды — сервер, папка — экспорт.
- **Прототип на stdlib** — честно: до 100 человек хватит, дальше Postgres и очередь (№40), это запланировано, не сюрприз.
