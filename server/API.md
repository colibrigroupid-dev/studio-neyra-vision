# Сервер хранения Neyra Vision · задачи №15–16, №31, №35

`server/app.py` использует только стандартную библиотеку Python 3.9+. Он раздаёт
публичные страницы репозитория и хранит проекты через JSON API. `studio/`
подключается к нему через настройку «Сервер» и «Ключ роли» (задача №16).
Подключение `scenariy/` — отдельная задача. Сервер не выполняет генерации и не проксирует
`/api/neyra` из существующего `scenariy/server.py`.

## Запуск и проверка

Из корня репозитория:

```sh
python3 server/app.py
python3 -m unittest discover -s server -p 'test_api.py' -v
```

Обычный запуск тестов открывает настоящий локальный TCP-сервер на свободном
порту. В песочнице Codex открытие TCP-порта запрещено; для неё есть режим:

```sh
NEYRA_TEST_TRANSPORT=inprocess python3 -m unittest discover -s server -p 'test_api.py' -v
```

Он передаёт HTTP-байты тому же обработчику внутри процесса. Это проверяет
маршруты, права и запись данных, но не доказывает, что сетевой порт можно открыть
в конкретном окружении. Сам сервер запускайте вне такой песочницы.

Адрес по умолчанию — `http://127.0.0.1:8770`. Параметры запуска:

```sh
python3 server/app.py --host 127.0.0.1 --port 8770 \
  --data-dir server/data \
  --keys-file ~/.config/neyra-studio/keys.json
```

Перед запуском оператор создаёт конфигурацию вне репозитория на основе
`server/keys.example.json`. Все поля `key` в примере намеренно пусты: сервер
отклоняет такой файл при запуске. Заполните их отдельными случайными секретами,
удалите ненужные записи и ограничьте `projects` и `sections`. Сам файл с
секретами и его копии в репозиторий не помещают.

```sh
mkdir -p ~/.config/neyra-studio
cp server/keys.example.json ~/.config/neyra-studio/keys.json
chmod 600 ~/.config/neyra-studio/keys.json
# Заполните key в этом внешнем файле перед запуском.
```

При указании собственного `--data-dir` не помещайте его в публичные папки
сайта. Данные по умолчанию лежат в `server/data/<slug>/project.json` и исключены
из git. На GitHub Pages этот Python-сервер не исполняется.

## Ключи, роли и разделы

Каждый запрос к `/api/` требует заголовок `X-Key`. Принимаются внешние ключи
из `keys.json` и ключи участников, выпущенные API проекта. Внешняя конфигурация
нужна для первого руководителя и имеет форму:

```json
{
  "keys": [
    {
      "id": "writer-local",
      "key": "",
      "role": "writer",
      "projects": ["demo"],
      "sections": ["overview", "script"]
    }
  ]
}
```

Это структура, а не рабочая конфигурация: `key` должен быть непустым секретом
из 1–512 печатных ASCII-символов без пробелов. ID и секреты уникальны.
`id` — открытый идентификатор ключа для ссылки из участника; секрет `key` API
не выдаёт. `projects` задаёт допустимые slug либо `["*"]` для всех проектов.
`sections: ["*"]` означает все разделы в пределах прав данной роли, а не
расширение её прав; в примере разделы перечислены явно.
Оператор создаёт внешние ключи в этом файле. API участников также умеет выпускать
свои случайные ключи: их SHA-256 хранится только в данных соответствующего
проекта, `keys.json` не меняется. Секрет выдаётся один раз в успешном ответе POST.
Клиент не задаёт секрет через поля `key` или `keyHash`.

Конфигурация строго проверяется при запуске и заново читается при каждом
API-запросе. Удаление ключа из неё отзывает доступ без перезапуска. Если файл
стал недоступен или невалиден, API возвращает 503 и не продолжает работу с
устаревшими правами. Это касается и входа по ключам участников: действующая
внешняя конфигурация остаётся обязательной. Значения ключей не попадают в
журнал HTTP-запросов.

Киношные разделы: `overview`, `script`, `breakdown`, `heroes`, `locations`,
`world`, `storyboard`, `shots`, `continuity`, `sound`, `edit`, `plan`, `journal`.
Сохранены разделы прежнего клиента `animatic`, `team`, `post`. Часть новых
разделов пока существует только как имя права; отдельного маршрута для неё нет.

| Роль | Допустимые разделы | Запись |
|---|---|---|
| `admin`, `producer` | Все | Да |
| `director` | Все, кроме `plan` | Да |
| `writer` | `overview`, `script`, `breakdown`, `journal`, `team` | `breakdown` только чтение |
| `assistant_director` | `overview`, `script`, `breakdown`, `journal`, `team` | Да; роль внешних ключей для карты №31 |
| `cinematographer` | `overview`, `storyboard`, `shots`, `continuity`, `journal`, `team` | Да |
| `artist` | `overview`, `heroes`, `locations`, `world`, `storyboard`, `shots`, `continuity`, `journal`, `team` | Да |
| `editor` | `overview`, `edit`, `sound`, `animatic`, `post`, `journal`, `team` | `sound` только чтение |
| `viewer` | Все, кроме `plan` | Нет |

Доступ к существующему проекту — пересечение роли, `projects` и `sections`
из конфигурации с членством и разделами участника этого проекта. Для ключа,
выпущенного API, роль и разделы берутся из актуальной записи участника,
а `projects` содержит только slug этого проекта. Одного
валидного ключа недостаточно для доступа к чужому проекту. `admin` может
работать без членства, но остаётся ограничен своей конфигурацией. Создавать
проекты могут `admin`, `director` и `producer`; создатель автоматически
становится участником. Управлять участниками могут эти роли с разделом `team`.
Имя автоматически созданного участника — «Создатель проекта»; реальное имя
можно вписать PATCH-запросом участника.
При создании или изменении участника разделы не могут превышать права его роли
и права руководителя, выполняющего запрос. Для связи с внешним `keyId` также
проверяются совпадение роли и ограничения этого ключа. Раздел `team` у
сценариста, художника или наблюдателя не даёт права управления командой.

Раздел `overview` открывает метаданные проекта, `script` — черновик, версии и
сцены, `shots` — кадры, `post` — задачи постпроизводства. Чтение команды требует
`overview`; изменение команды — `team` и роль руководителя. Получение проекта
возвращает метаданные, `principal` и `capabilities.manageTeam`: оно не раскрывает
сценарий, кадры или команду обходом их прав.
Изменять метаданные могут только `admin`, `director`, `producer`. Роль `artist`
получает кадры с `sceneId`, но список сцен и их текст через этот контракт не
читает. Выбор сцен в клиенте потребует отдельного решения о доступе к их
идентификаторам и названиям.

Для примеров ниже введите ключ нужной роли и сохраните его в локальной
переменной оболочки:

```sh
read -r -s NEYRA_KEY
```

## Подключение `studio/`

Настройки «Сервер» (по умолчанию `http://127.0.0.1:8770`) и «Ключ роли»
хранятся в localStorage только на текущем устройстве. Адрес — HTTP(S) origin
сервера; ключ отправляется в `X-Key`, без URL-параметров и без cookies.
Подключённый клиент читает и записывает серверные проекты, сцены, кадры,
участников, черновик, версии и задачи поста. Локальные проекты остаются
отдельными данными браузера: подключение само по себе не переносит их на сервер.

Шапка показывает «сохранено на сервере» только после подтверждения запросов;
во время записи — «сохраняется на сервере…», при отказе — ошибку. Без ключа
или при недоступном сервере используется localStorage и надпись
«только в этом браузере». Если связь пропала во время записи, клиент создаёт
локальные копии текущих серверных проектов, сохраняя прежние проекты браузера;
сам не отправляет эти копии обратно при следующем подключении. Ошибка записи
в браузер также показывается как ошибка. Повторное подключение — через «Сервер»;
пустой ключ возвращает к локальным проектам.

При создании серверного проекта можно задать «Код проекта (латиница)» — slug
для ограничений `projects` в конфигурации ключей. Без кода клиент создаёт UUID.
Менеджер создаёт проект, затем в «Команде» добавляет человека по имени и e-mail,
выбирает роль и разделы. После сохранения ключ показан один раз с кнопкой
«Скопировать». Передайте ключ лично; письмо на e-mail подключим позже.
Временный показ секрета не сохраняется в данных проекта или localStorage.
Участник использует полученный ключ в настройке подключения «Сервер».

В разделе сценария доступен «Черновик целиком» из `/script`, отдельно от сцен.
Изменение сцен пересобирает черновик; если прежний полный текст отличался от
собранных сцен, он предварительно добавляется отдельной сценой
«Сохранённый черновик». Импорт TXT добавляет сцену, сохраняя прежний текст.
Локальная копия при потере связи сохраняет также самостоятельные черновики
и тексты исторических версий. Смена RU/KZ интерфейса не меняет текст сценария.

Менеджер с ключом `admin`, `director` или `producer` и доступом `team` создаёт
участника и его ключ в одном запросе:

```sh
# NEYRA_KEY здесь — ключ менеджера. Поле key ответа покажется один раз.
curl -H "X-Key: $NEYRA_KEY" -H 'Content-Type: application/json' \
  --data '{"name":"Сценарист","email":"writer@example.test","role":"writer","sections":["overview","script"]}' \
  http://127.0.0.1:8770/api/projects/demo/members
```

Старый вариант с `keyId` внешнего ключа сохранён для существующих интеграций.
Одного `projects: ["demo"]` у внешнего ключа недостаточно: до добавления
участника он не открывает `demo`, а список проектов для него пуст. Сценаристу для
списка проектов и сценария нужны оба раздела `overview` и `script`. То же
правило членства действует для остальных ролей; исключения — `admin` и
автоматическое членство создателя проекта. Клиент не расширяет права ключа и
не добавляет участника от имени роли, у которой нет `team`.

Для клиентов с другого HTTP(S) origin сервер поддерживает CORS: preflight
`OPTIONS /api/...` не требует `X-Key`, разрешает методы GET/POST/PUT/PATCH/DELETE
и заголовки `X-Key`, `Content-Type`, `If-Match`. Ответ отражает корректный
HTTP(S) `Origin`, имеет `Vary: Origin` и открывает чтение `ETag`; это действует
также для ошибок 401/403/409/500. Cookies и `Access-Control-Allow-Credentials`
не используются. `Origin: null` (например, `file://`) не поддерживается —
открывайте страницы через HTTP-сервер. CORS не отменяет ограничений браузера
на смешанное содержимое и доступ к локальной сети.

## Общие правила запросов и ответов

Базовый путь — `/api/projects`. Тело POST, PUT и PATCH — JSON-объект с
`Content-Type: application/json` и одним корректным `Content-Length`; chunked
`Transfer-Encoding` не поддерживается. Максимальный размер тела — 2 МиБ.
Исключение — POST восстановления версии: он принимает пустое тело без
`Content-Type` и с `Content-Length: 0` либо без `Content-Length`; клиент `studio/`
передаёт `{}` как обычный JSON. У остальных POST/PUT/PATCH тело обязательно.
Неизвестные поля и неверные типы отклоняются. Повторяющиеся поля JSON, `NaN` и
`Infinity` не допускаются. Даты выдаются в UTC; идентификаторы и даты создаёт
сервер. Slug — 1–64 строчных латинских букв, цифр и дефисов, начинается и
заканчивается буквой или цифрой. ID — 1–80 латинских букв любого регистра,
цифр, дефисов и подчёркиваний, начинается буквой или цифрой. `/`, `..` и обход
путей недопустимы.

Успешный ответ:

```json
{"data":{"slug":"demo","title":"Рабочий проект"}}
```

Ответ списка:

```json
{"data":[],"pagination":{"offset":0,"limit":50,"total":0}}
```

Все списки поддерживают `?offset=0&limit=50`: `offset` — целое от нуля, `limit`
— целое от 1 до 200 (по умолчанию 50). `total` — число доступных элементов до
ограничения страницы. Список проектов содержит только проекты, доступные ключу
по разделу `overview`. Исключение — `GET /map`: вся карта возвращается одним
ответом, без пагинации.

Успешные ответы конкретного проекта содержат `ETag: "<revision>"`. Любая его мутация
может принять `If-Match: "<revision>"`: устаревшая ревизия даёт
`409 REVISION_CONFLICT`, данные не меняются. Без `If-Match` запрос применяется
к последнему состоянию. POST создаёт новые записи; автоматический повтор такого
запроса может создать ещё одну версию или сущность. Ключей идемпотентности нет.

Пользовательские строки хранятся и после JSON-декодирования возвращаются
дословно. В HTTP JSON символы `<`, `>` и `&` экранируются как `\u003c`, `\u003e`,
`\u0026`; ответы имеют JSON MIME-тип. Клиент выводит строки через `textContent`
или экранирование текста, без подстановки в `innerHTML`. Это сохраняет Fountain
и исходный текст, включая русский и казахский.

Общие статусы кадров и сценария: `draft`, `working`, `review`, `approved`.
Поле `language` принимает `ru` или `kk`; смена этого поля не переводит текст.
При PUT без `status` черновик получает `draft`; без `language` сохраняет свой
нынешний язык. Язык в метаданных проекта и язык черновика после создания
изменяются независимо.

Необязательный `translations` сохраняет оба языка интерфейса без потери
канонических полей старого API. Это объект с необязательными ключами `ru` и
`kk`, других языков нет. В метаданных проекта языковые значения — объекты
с полями `title`, `synopsis`; в сценах — `title`, `text`; в кадрах — `title`,
`description`, `prompt`, `movement`. Поля внутри перевода необязательны,
пустые строки допустимы, лимиты совпадают с соответствующими основными полями.
Неизвестные поля и неверные типы дают 422. POST/PATCH без `translations` не
удаляет существующий перевод; явное поле заменяет весь объект переводов.
Основные поля не меняются при передаче только перевода.

## Проекты

| Метод и путь | Назначение | Тело | Успех |
|---|---|---|---|
| `POST /api/projects` | Создать | `slug`, `title`; необязательно `synopsis`, `language`, `translations` | 201 |
| `GET /api/projects` | Список доступных проектов | — | 200 |
| `GET /api/projects/<slug>` | Метаданные проекта | — | 200 |
| `PATCH /api/projects/<slug>` | Обновить метаданные | Любые из `title`, `synopsis`, `language`, `translations` | 200 |

Метаданные: `slug`, `title`, `synopsis`, `language`, `createdAt`, `updatedAt`,
`revision`, необязательный `translations`. `title` — непустая строка до 240 символов, `synopsis` — строка до
8000 символов; язык по умолчанию `ru`. Slug после создания не меняется.
GET конкретного проекта дополнительно возвращает `principal: {id, role,
projects, sections}` и `capabilities: {manageTeam}` для текущего ключа.
GET `/api/session` возвращает `data: {id, role, projects, sections}` без секрета
и хэша; другие методы этого маршрута дают 405.

```sh
curl -i -H "X-Key: $NEYRA_KEY" -H 'Content-Type: application/json' \
  --data '{"slug":"demo","title":"Рабочий проект","language":"ru"}' \
  http://127.0.0.1:8770/api/projects
curl -H "X-Key: $NEYRA_KEY" 'http://127.0.0.1:8770/api/projects?offset=0&limit=20'
curl -i -H "X-Key: $NEYRA_KEY" http://127.0.0.1:8770/api/projects/demo
curl -X PATCH -H "X-Key: $NEYRA_KEY" -H 'Content-Type: application/json' \
  --data '{"synopsis":"Замысел проекта"}' \
  http://127.0.0.1:8770/api/projects/demo
```

## Черновик и версии сценария

| Метод и путь | Назначение | Тело | Успех |
|---|---|---|---|
| `GET /api/projects/<slug>/script` | Текущий черновик | — | 200 |
| `PUT /api/projects/<slug>/script` | Заменить текст черновика | `text`; необязательно `language`, `status`, `translations` | 200 |
| `POST /api/projects/<slug>/versions` | Зафиксировать черновик и сцены | Необязательно `label` | 201 |
| `GET /api/projects/<slug>/versions` | Список версий | — | 200 |
| `GET /api/projects/<slug>/versions/<id>` | Получить версию | — | 200 |
| `POST /api/projects/<slug>/versions/<id>/restore` | Восстановить версию, сохранить текущий черновик | `{}` либо пустое тело | 201 |

`text` — строка Fountain или обычного текста до 1 000 000 символов. Пустой текст
допустим. Черновик
имеет `text`, `language`, `status`, `updatedAt`; новая версия фиксирует объект
`script` с этими полями и массив
`scenes`. Поля версии: `id` (UUID без дефисов), `number` (последовательный номер),
`kind` (`saved`, `backup`, `restored`), `label`, `script`,
`scenes`, `createdAt`, `createdBy`; у восстановленной версии есть
`sourceVersionId`. `label` — строка до 240 символов. Список версий выдаёт только
метаданные, без `script` и `scenes`; полные снимки возвращаются при создании
версии и запросе конкретного ID.

У черновика `translations` имеет форму `{"ru":"Текст","kk":"Мәтін"}`,
каждый текст — до 1 000 000 символов. `text` каноничен для `script.language`:
если карта переводов существует или передана, сервер синхронизирует запись
текущего языка с `text`. PUT без `translations` сохраняет другой язык.
PUT с явным объектом заменяет карту; затем сервер синхронизирует текущий язык.
Версии и резервный черновик сохраняют `translations` сценария и сцен.

При восстановлении одна атомарная запись сохраняет текущий черновик со сценами
в версии `backup`, создаёт версию `restored` из выбранной и заменяет черновик
со сценами. Восстановленный черновик получает статус `draft` и актуальный
`updatedAt`, даже если у исходной версии был другой статус. Старые версии
остаются. Ответ:

```json
{
  "data": {
    "script": {"text":"...","language":"ru","status":"draft"},
    "backupVersionId":"идентификатор резервной версии",
    "restoredVersionId":"идентификатор восстановленной версии"
  }
}
```

Изменение текста черновика помечает кадры `needsReview: true`. Восстановление также
оставляет все материалы кадров и помечает их для проверки. Если сцена кадра
отсутствует в восстановленной версии, кадр не удаляется: клиент должен показать

не меняет черновик.

curl -X PUT -H "X-Key: $NEYRA_KEY" -H 'Content-Type: application/json' \

curl -H "X-Key: $NEYRA_KEY" -H 'Content-Type: application/json' \

curl -H "X-Key: $NEYRA_KEY" http://127.0.0.1:8770/api/projects/demo/versions
# Подставьте id из ответа списка или создания версии.

## Кадры

| Метод и путь | Назначение | Тело | Успех |
|---|---|---|---|
| `GET /api/projects/<slug>/shots` | Список | — | 200 |
| `POST /api/projects/<slug>/shots` | Создать | `sceneId`, `title`; необязательные поля ниже | 201 |
| `GET /api/projects/<slug>/shots/<id>` | Получить | — | 200 |
| `PATCH /api/projects/<slug>/shots/<id>` | Изменить | Любые изменяемые поля ниже | 200 |
| `DELETE /api/projects/<slug>/shots/<id>` | Удалить | — | 200 |

`sceneId` должен ссылаться на существующую сцену, иначе ответ 404. `title` —
непустая строка до 240 символов.
Допустимы строки `description`, `prompt`, `owner`, `lens`, `movement`,
до 8000 символов; `imageUrl`, `videoUrl` — до 2048 символов. `duration` —
конечное число секунд больше 0 и не больше 3600 (по умолчанию 5); `status` —
`draft`, `working`, `review`, `approved` (по умолчанию `draft`).
При создании можно передать безопасный `id`; при PATCH он неизменяем.
`aspectRatio` сервер устанавливает в `16:9`, `needsReview` управляется сервером.
PATCH со статусом `approved` снимает `needsReview`. Поля `imageUrl` и `videoUrl`
содержат пустую строку, HTTP/HTTPS-ссылку или относительный путь; другие схемы и
ссылки вида `//host/path` отклоняются. Загрузки файлов и получения содержимого
по ссылке этим API нет.

Необязательный `comments` — список до 500 объектов с обязательными строками
`author` (непустая, до 240 символов), `text` (до 8000), `date` (до 80).
`date` сохраняет исходную текстовую метку клиента, сервер не приписывает ей
смысл UTC-времени. PATCH с `comments` заменяет весь список, без поля оставляет
его прежним. Комментарии и переводы выдаются с тем же экранированием JSON, что
и остальные пользовательские строки. При обновлении полного списка клиент
использует `If-Match`, чтобы чужой комментарий не потерялся при параллельной правке.

```sh
curl -H "X-Key: $NEYRA_KEY" -H 'Content-Type: application/json' \
  --data '{"id":"shot-1","sceneId":"scene-1","title":"Общий план","description":"Комната","status":"draft","duration":4}' \

curl -H "X-Key: $NEYRA_KEY" http://127.0.0.1:8770/api/projects/demo/shots
curl -H "X-Key: $NEYRA_KEY" http://127.0.0.1:8770/api/projects/demo/shots/shot-1
curl -X PATCH -H "X-Key: $NEYRA_KEY" -H 'Content-Type: application/json' \
  --data '{"status":"review"}' \
  http://127.0.0.1:8770/api/projects/demo/shots/shot-1
curl -X DELETE -H "X-Key: $NEYRA_KEY" \
  http://127.0.0.1:8770/api/projects/demo/shots/shot-1
```

## Задачи постпроизводства

| Метод и путь | Назначение | Тело | Успех |
|---|---|---|---|
| `GET /api/projects/<slug>/post` | Текущее состояние | — | 200 |
| `PUT /api/projects/<slug>/post` | Заменить список задач | `tasks` | 200 |

Ответ имеет вид `{"data":{"tasks":[{"id":"edit","done":true}]}}`.
`tasks` — список от нуля до четырёх объектов; `id` — один из `edit`, `color`,

сохранённое состояние. В файле проекта `post` хранит массив задач.

## Участники · №35

| Метод и путь | Назначение | Тело | Успех |
|---|---|---|---|
| `GET /api/projects/<slug>/members` | Список | — | 200 |
| `POST /api/projects/<slug>/members` | Добавить и выпустить ключ | `name`, `email`, `role`, `sections` | 201 |
| `GET /api/projects/<slug>/members/<id>` | Получить | — | 200 |
| `PATCH /api/projects/<slug>/members/<id>` | Изменить права | Любые из `name`, `email`, `role`, `sections` | 200 |
| `DELETE /api/projects/<slug>/members/<id>` | Отозвать ключ | — | 200 |

GET доступен всем участникам с `overview`, включая наблюдателя. POST/PATCH/DELETE
доступны `admin`, `producer`, `director` с `team`. `name` — непустая строка
до 240 символов. `email` — корректный адрес до 254 символов; крайние пробелы
удаляются. Активный адрес в проекте уникален без учёта регистра: повтор даёт
409 `ALREADY_EXISTS`. `sections` — непустой список явных разделов без повторов
(`*` здесь не принимается). Роль — `producer`, `director`, `writer`,
`cinematographer`, `artist`, `editor`, `viewer`; `admin` через этот POST не
выпускается. Раздел за пределами роли даёт 422; за пределами прав выдающего
руководителя — 403. Поля `key`, `keyHash`, `keyId`, `accessStatus` и серверные
даты для выпуска и изменения такого ключа клиент не задаёт.

Ответ выпуска — `{"data":{...участник...},"key":"..."}` и ETag новой ревизии.
Сервер создаёт ID участника, `keyId: "member-<id>"`, `createdAt` и ключ вида
`nv1.<slug>.<keyId>.<случайный секрет>`. Случайная часть — 32 байта из
`secrets.token_urlsafe(32)`; SHA-256 полного ключа сохраняется как `keyHash`
только в `project.json`. Исходный ключ после успешной записи возвращается один
раз. При отказе записи секрет не выдаётся. Конфигурация `keys.json` не меняется.

Публичная запись содержит `id`, `name`, `email`, `role`, `keyId`, `sections`,
`createdAt`, при отзыве `revokedAt`, а также `keySource` (`issued` или `external`)
и `accessStatus` (`active`, `revoked`, `unavailable`). У старых записей e-mail и
дата создания могут отсутствовать. GET, PATCH, DELETE, проект, сессия, версии и
лента не возвращают ключ или его хэш. PATCH меняет права на следующем запросе
без перезапуска. DELETE удаляет хэш, оставляет участника с `revokedAt` и
`accessStatus: "revoked"`, возвращает его публичную запись; бывший ключ сразу
даёт 401. Повторный DELETE сохраняет факт отзыва. PATCH отозванной записи даёт
409 `ACCESS_REVOKED`; для нового доступа создайте нового участника.

Для прежних интеграций сохранён POST `name`, `role`, `sections`, `keyId`: он
связывает участника с уже существующим внешним ключом, не выпускает новый и
не возвращает поле `key`. Неизвестный `keyId`, другая роль или разделы сверх
прав внешнего ключа дают 422. DELETE такой связи удаляет участника и возвращает
`data: {"id":"...","deleted":true}`; значение внешнего ключа остаётся в
конфигурации. Внешний `admin` может входить без членства, поэтому удаление его
связи с проектом не отзывает глобальный ключ: его отзывает оператор в `keys.json`.
DELETE сцены и кадра по-прежнему возвращает `{id, deleted:true}`.

```sh
# Используйте ключ admin/director/producer с team и правами выдаваемых разделов.
curl -H "X-Key: $NEYRA_KEY" -H 'Content-Type: application/json' \
  --data '{"name":"Сценарист","email":"writer@example.test","role":"writer","sections":["overview","script"]}' \
  http://127.0.0.1:8770/api/projects/demo/members
curl -H "X-Key: $NEYRA_KEY" http://127.0.0.1:8770/api/projects/demo/members
NEYRA_MEMBER_ID='id-из-ответа'
curl -H "X-Key: $NEYRA_KEY" \
  "http://127.0.0.1:8770/api/projects/demo/members/$NEYRA_MEMBER_ID"
curl -X PATCH -H "X-Key: $NEYRA_KEY" -H 'Content-Type: application/json' \
  --data '{"role":"viewer","sections":["overview","script"]}' \
  "http://127.0.0.1:8770/api/projects/demo/members/$NEYRA_MEMBER_ID"
curl -X DELETE -H "X-Key: $NEYRA_KEY" \
  "http://127.0.0.1:8770/api/projects/demo/members/$NEYRA_MEMBER_ID"
```

## Карта производства и апрувы · №31

Карта хранится в том же файле проекта, что сцены и кадры. Клетка обозначает
один объект на одном этапе. В рамках проекта пара `object + stage` уникальна:
повторное создание даёт 409. Незаполненное сочетание в `grid` выдаётся как
`null`; клиент показывает его как `empty`. Записи клеток создаются явно.

| Метод и путь | Назначение | Успех |
|---|---|---|
| `GET /api/projects/<slug>/map` | Вся сохранённая карта, «мои задачи», «ждёт меня» | 200 |
| `GET /api/projects/<slug>/cells` | Список клеток с обычной пагинацией | 200 |
| `POST /api/projects/<slug>/cells` | Создать клетку | 201 |
| `GET /api/projects/<slug>/cells/<id>` | Одна клетка | 200 |
| `PATCH /api/projects/<slug>/cells/<id>` | Обновить клетку | 200 |
| `GET /api/projects/<slug>/approvals` | История вердиктов с обычной пагинацией | 200 |
| `GET /api/projects/<slug>/approvals/<id>` | Один вердикт | 200 |
| `POST /api/projects/<slug>/approvals` | Принять или вернуть представленную версию | 201 |
| `GET /api/projects/<slug>/activity` | Лента операций с обычной пагинацией | 200 |
| `GET /api/projects/<slug>/activity/<id>` | Одна операция | 200 |

DELETE клеток не поддерживается. Истории `approvals` и `activity` только
дописываются: PUT, PATCH и DELETE возвращают 405. Клиент не создаёт записи
`activity`: журнал заполняет сервер при успешных изменениях.

Все новые маршруты требуют раздел `overview`. Чтение клетки и истории
показывает общие метаданные проекта; запись клетки или апрува дополнительно
требует права записи в разделе её этапа.

### Клетка

Тело POST:

```json
{
  "object": {"type":"scene","id":"scene-1"},
  "stage": "storyboard",
  "assignee": {"keyId":"operator-local","name":"Оператор"},
  "approverRole": "director",
  "status": "empty",
  "dueAt": null,
  "comment": "",
  "version": null,
  "variant": null
}
```

Обязательны `object` и `stage`. Сервер добавляет `id` (UUID), `project` (slug),
`createdAt` и `updatedAt`. `object.type` — `scene`, `shot`, `teaser` или
`episode`; `object.id` — безопасный ID по общим правилам. Для `scene` и `shot`
объект должен существовать в этом проекте, иначе 404. Тизер и серия пока имеют
только идентификатор строки карты: отдельных сущностей и состава серии в этом
API нет.

`stage` — `script`, `breakdown`, `heroes`, `locations`, `storyboard`, `shots`,
`video`, `sound`, `edit`. `status` — `empty`, `working`, `done`, `awaiting`,
`approved`, `returned`. При создании по умолчанию `empty`; назначение без
исполнителя — `assignee: {"keyId":null,"name":""}`, без срока — `dueAt: null`,
без комментария — `comment: ""`, без версии и варианта — `null`.
`dueAt` принимает дату `YYYY-MM-DD` или дату со временем ISO 8601 с часовым
поясом и разделителем `T`; это срок клиента, а не время операции. Если
назначен `keyId`, принимается активный ключ участника или внешней конфигурации;
проверяются ключ, проект, членство и право записи в разделе
этапа (с обычным исключением членства для `admin`). Пустое имя при назначенном
ключе заполняется именем участника, либо ID ключа. Имя можно задать и без
ключа; такая клетка не попадает в «мои задачи» ни для какого ключа.
`assignee.name`, `version` и `variant` — строки до 240 символов;
версия/вариант должны быть непустыми, либо `null`. `comment` — до 8000,
`dueAt` — до 80 символов. Версия и вариант — метки представленного результата;
существование отдельного файла с такой меткой не проверяется.

Создавать клетки и менять назначение, утверждающую роль или срок могут только
`admin`, `director`, `producer` с доступом к разделу этапа. Назначенный
исполнитель с тем же доступом может PATCH-поля `status`, `comment`, `version`,
`variant`. ID, проект, объект, этап и серверные даты не изменяются.
`approved` и `returned` нельзя выставить POST/PATCH клетки: это 422,
вердикт оформляется через `/approvals`. Чтобы запросить утверждение,
исполнитель сохраняет версию и/или вариант и переводит клетку в `awaiting`.
Прежнее поле `status` сценария/кадра само по себе не утверждает клетку и не
выполняет зависимости карты.

### Утверждающие и доступы

| Этап | Раздел прав | Утверждающий по умолчанию | Другие допустимые утверждающие |
|---|---|---|---|
| `script` | `script` | `producer` | `writer` |
| `breakdown` | `script` | `assistant_director` | — |
| `heroes` | `storyboard` | `director` | — |
| `locations` | `storyboard` | `director` | — |
| `storyboard` | `storyboard` | `director` | `cinematographer` |
| `shots` | `shots` | `director` | — |
| `video` | `animatic` | `director` | — |
| `sound` | `post` | `director` | — |
| `edit` | `post` | `producer` | `director` |

Таблица сохраняет разделы внешних ключей №31. Для ключей участников №35
раздел совпадает с именем этапа (`breakdown`, `heroes`, `locations`, `sound`,
`edit`), кроме `video`, которому соответствует `animatic`. Поэтому сценарист
может читать разбивку, но не быть её исполнителем или менять её клетку;
монтажёр читает звук, но не выполняет и не меняет звуковую клетку. Художник
может работать с клеткой `heroes` по праву `heroes`, без `storyboard`.

На клетку назначается одна утверждающая роль. Вердикт может поставить только
участник с `role == approverRole`, либо `admin`/`producer`. Во всех случаях
проверяются ограничения ключа на проект и раздел этапа и членство в проекте
(для `admin` действует обычное исключение членства). `viewer` не утверждает.
Одного попадания в список «ждёт меня» недостаточно для обхода этих проверок.

### Апрув

POST `/api/projects/<slug>/approvals`:

```json
{
  "object": {"type":"scene","id":"scene-1"},
  "stage": "storyboard",
  "version": "draft-2",
  "variant": null,
  "verdict": "approved",
  "comment": ""
}
```

Обязательны объект, этап, `verdict` (`approved` или `returned`) и версия и/или
вариант представленного результата. Связанная клетка должна быть `awaiting`;
переданные `version` и `variant` должны совпадать с её текущими значениями.
Несовпадение или повторный вердикт по уже закрытому ожиданию дают 409. Другая
роль даёт 403. Автор (`keyId`) и время (`createdAt`) берутся из ключа и часов
сервера; клиент не может передать чужого автора или задним числом поставить
дату. Сервер добавляет `id`, `project`, `cellId`, объект, этап, версию/вариант,
вердикт и комментарий в историю и меняет статус клетки в той же атомарной
записи. Последующая правка клетки и новый апрув сохраняют прежние вердикты.

Правка представленной версии/варианта или утверждающей роли без явного нового
статуса возвращает утверждённую либо ожидающую клетку в `done`: требуется
новое представление и вердикт. Новый вариант можно отправить в `awaiting`
тем же PATCH, явно указав этот статус. Изменение текста/переводов сценария,
правка сцены/кадра, добавление или удаление кадра сцены либо восстановление версии также
сбрасывает связанные текущие утверждения; прежние записи апрувов остаются
в истории. Удаление сцены или кадра, используемых клетками, даёт 409
`OBJECT_IN_MAP`.

### Зависимости

Проверка срабатывает при создании или явной установке `working`, `done`,
`awaiting` и при вердикте `approved`. Правка комментария, срока или назначения
без установки такого статуса доступна и у заблокированной задачи.
Требуются именно клетки в статусе `approved`:

- `shots` сцены — её `storyboard` и `heroes`;
- `video` сцены — её `shots`;
- `edit` — `video` всех текущих сцен проекта; проект без сцен не проходит;
- клетка кадра (`shot`) использует зависимости его родительской сцены;
- `shots` и `video` тизера/серии используют предыдущие этапы этого же объекта.

Нарушение даёт 409 с сообщением о непринятых этапах; клетка и журнал не
меняются. Для `edit` любого объекта, в том числе тизера/серии, пока проверяются
все сцены проекта: группировка
сцен по сериям ещё не реализована. Остальные независимые клетки могут
выполняться параллельно.

### Карта и личные списки

GET `/api/projects/<slug>/map` требует раздел `overview` и возвращает
`data: {project, stages, objects, grid, cells, myTasks, awaitingMe}`. `cells`
содержит все сохранённые клетки без пагинации; `stages` — этапы в
производственном порядке от `script` до `edit`; `project` — slug. Запрос не
принимает параметры: даже `offset`/`limit` дают 400. `objects` содержит ссылки на
все текущие сцены и кадры и остальные объекты из клеток, включая тизеры/серии
и сцены, оставшиеся только в карте после восстановления старой версии. `grid` —
полная матрица строк `{object, stages: {script: cell-or-null, ...}}`; `null`
означает, что клетка ещё не создана. Карта общая для участников, содержит
метаданные задач без текста сцен и промптов кадров. Запись и утверждение
остаются ограничены разделом этапа.

`myTasks` — клетки, где `assignee.keyId` совпадает с ключом запроса.
`awaitingMe` — клетки `awaiting`, которые этот ключ вправе утвердить с учётом
роли и раздела этапа. Для `admin` и `producer` учитывается право утверждать
вместо назначенной роли. Имя исполнителя не используется как идентификатор
доступа.

### Лента и журнал происхождения

GET `/activity` выдаёт серверные операции в порядке добавления. Запись хранит
`id`, последовательный `sequence`, `keyId`, `name`, `createdAt`, `action`,
`object: {type, id}`, `contentHash`, `previousHash`, `hash`. Для операций клетки
и апрува дополнительно сохраняются `stage`, `cellId`, `version`, `variant`,
`status`, а для вердикта — `approvalId`: состояние и версия видны в событии,
даже если клетка впоследствии изменится. При сбросе утверждений событие также содержит
`invalidatedCellIds`. Успешные операции существующих маршрутов (проекты,
сценарий и его версии, сцены, кадры, участники,
пост) также попадают в ленту. Отказы, чтение и неуспешные записи не создают
событий. Секрет `X-Key` в журнал не попадает.

`contentHash` — SHA-256 канонического JSON данных ответа успешной мутации;
это не хэш внешнего файла. `hash` — SHA-256 канонического JSON самой записи
без поля `hash`; `previousHash` связывает её с предыдущей. Канонический JSON:
UTF-8, `ensure_ascii=False`, `sort_keys=True`, `separators=(',', ':')`.
У первой записи `sequence: 1` и `previousHash: null`. Сервер проверяет цепочку
при чтении файла проекта; разрыв или неверный хэш дают 500 `STORAGE_READ_FAILED`.
Это основа журнала операций из §6 концепта, позволяющая проверить
последовательность сохранённых записей. Хэш-цепочка
не является электронной подписью и не защищает от полной замены журнала
человеком с доступом к файлам сервера.

Старые файлы проектов без `cells`, `approvals` или `activity` читаются как
с пустыми массивами; они сохранятся при следующей успешной записи. Прошлые
операции не восстанавливаются выдуманными событиями. Полный журнал
происхождения файлов (инструмент, модель, промпт, параметры, цена, права),
генерации и экспорт дата-рума в №31 не реализованы.

## Ошибки и гарантии хранения

Ошибки возвращаются JSON-объектом с HTTP-кодом ошибки:

```json
{"error":{"code":"FORBIDDEN","message":"Недостаточно прав"}}
```

| HTTP | `error.code` | Смысл |
|---|---|---|
| 400 | `INVALID_JSON` | Синтаксис JSON/UTF-8 неверен, тело оборвано, повторены поля либо переданы NaN/Infinity |
| 400 | `BAD_REQUEST` | JSON синтаксически корректен, но верхний уровень не объект (`[]`, строка, число, boolean, null); неверная форма HTTP-запроса, preflight, пути, параметров или If-Match |
| 401 | `UNAUTHORIZED` | Нет ключа или ключ неверен |
| 403 | `FORBIDDEN` | Нет права на проект, раздел или запись |
| 404 | `NOT_FOUND` | Нет маршрута, проекта или сущности |
| 405 | `METHOD_NOT_ALLOWED` | Метод не поддерживается маршрутом |
| 409 | `ALREADY_EXISTS` | Такой slug или ID уже существует |
| 409 | `REVISION_CONFLICT` | `If-Match` не совпадает с ревизией |
| 409 | `SCENE_IN_USE` | Сцену используют кадры |
| 409 | `DEPENDENCY_CONFLICT` | Не утверждены необходимые предыдущие этапы |
| 409 | `CELL_NOT_AWAITING` | Клетка не ожидает вердикта |
| 409 | `APPROVAL_CONFLICT` | Версия/вариант вердикта не совпадает с представленным результатом |
| 409 | `OBJECT_IN_MAP` | Объект используется клетками карты |
| 409 | `ACCESS_REVOKED` | Права отозванного участника нельзя восстановить PATCH-запросом |
| 413 | `PAYLOAD_TOO_LARGE` | Тело больше 2 МиБ |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | Тело передано не как JSON |
| 422 | `VALIDATION_ERROR` | Некорректные поля, ссылки, роль или разделы |
| 500 | `STORAGE_READ_FAILED` | Не удалось прочитать состояние проекта |
| 500 | `STORAGE_WRITE_FAILED` | Не удалось записать состояние проекта |
| 500 | `IO_ERROR` | Ошибка ввода-вывода, в том числе при обработке HTTP |
| 500 | `INTERNAL_ERROR` | Внутренняя ошибка без выдачи деталей или трассировки |
| 503 | `KEYS_UNAVAILABLE` | Конфигурация ключей стала недоступной или неверной |

Каждый проект записывается одним JSON-файлом: временный файл в той же папке,
`fsync`, затем атомарная замена (`os.replace`). Внутрипроцессная блокировка
сериализует операции параллельных HTTP-потоков, включая проверку ревизии и
восстановление. При ошибке до замены старый файл остаётся целым и запрос
возвращает ошибку, а не 200. Фиксация резервной и восстановленной версий вместе
с черновиком не разбивается на отдельные записи.

Данные сохраняются после перезапуска. Поддерживается один процесс сервера на
один каталог данных; межпроцессной блокировки и совместного редактирования в
реальном времени нет.

Статика доступна без `X-Key` только из разрешённых публичных путей и типов
файлов: публичные корневые файлы, `assets/`, `studio/`, `scenariy/`, `p/`.
Разрешённые типы — HTML, CSS, JS/MJS, изображения, шрифты, видео и аудио;
разрешён и корневой `version.txt`. `server/`, скрытые файлы, `.git`, JSON,
исходники Python, Markdown и внешние
символьные ссылки не раздаются; списка содержимого папок нет. Конфигурация
ключей, данные и внутренние документы не выдаются HTTP-сервером.
