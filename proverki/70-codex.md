## Находки

### 1. 🔴 Повторный возврат токенов после отказа записи проекта · №69

**Место:** `server/app.py:1301`, `server/app.py:1302`, `server/app.py:1307`.

Возврат сначала фиксируется в `tokeny.json`, затем отметка `vozvrat` и конечный статус сохраняются в `project.json`. Два атомарных файла не образуют одну транзакцию.

**Воспроизведение:** участник с балансом 300 запускает фиктивное видео за 128; баланс 172, задание `queued`. Подменить `video.status` ответом `failed`, а `store.save(project)` — `ApiError(500, STORAGE_WRITE_FAILED, ...)`. Первый GET `/video` возвращает 500, баланс уже 300, на диске задание по-прежнему `queued`, `vozvrat` отсутствует. Убрать отказ записи, повторить GET: баланс **428**, записаны **два возврата** одного задания. Обычный повтор GET после успешной записи возвращает один раз — дефект именно в восстановлении после сбоя.

**Нужно:** возврат с устойчивым идентификатором задания и проверкой уже проведённой операции в кошельке; согласованная фиксация состояния и возврата.

### 2. 🔴 Оплаченная задача теряется при отказе записи; повтор запускает и оплачивает вторую · №69

**Место:** `server/app.py:2004`, `server/app.py:2011`, `server/app.py:2013`, `server/app.py:2272`. Аналогичное раздельное сохранение кошелька и проекта: кадры `server/app.py:2065`, картинка `server/app.py:2104`.

**Воспроизведение:** mock `video.create` возвращает `provider-task-one`; подменить только `store.save(project)` ошибкой. POST `/shots/<id>/video` → **500**, баланс **300 → 172**, сохранённых заданий **0**. Это не списание до ответа провайдера: проблема между успешным созданием и устойчивой записью задания.

**Нужно:** устойчивое задание/журнал операции, возможность восстановить созданный task ID и идемпотентность повторной попытки; согласованная фиксация списания и результата. Возврат токенов сам по себе не отменяет уже созданную задачу провайдера.

### 4. 🔴 Клиент прерывает генерацию через 4 секунды, сервер продолжает работу · №70/69

**Место:** `studio/app.js:361`, `studio/app.js:1148`; причина — `studio/storage.js:143`. Синхронная генерация — `server/app.py:2096`.

Новые операции используют общий клиент с тайм-аутом 4 с. Сам интерфейс обещает для картинки 10–30 с (`studio/app.js:1147`). Истечение тайм-аута не останавливает Handler и не откатывает серверную операцию.

**Воспроизведение:** фактическому `StudioServer.request` дать fake fetch, реагирующий на AbortSignal, и отдельную имитацию серверного завершения через 4200 мс. Клиент выдаёт `NETWORK_ERROR` через **4004 мс**, серверное завершение наступает позже. `directorCall` показывает ошибку и не загружает результат; блокировка UI снимается. Реальное ожидание генерации/создания/опроса также может превышать 4 с. Второе списание здесь не неизбежно: оставшийся старый If-Match иногда остановит повтор, но пользователь всё равно получает ложную ошибку оплаченной операции.

**Нужно:** очередь с опросом и восстановлением результата либо подходящий тайм-аут плюс обработка неопределённого исхода; не предлагать повтор платного вызова без выяснения результата предыдущего.

### 10. 🟡 GET `/video` меняет сохранённый проект без изменения ревизии · №69
